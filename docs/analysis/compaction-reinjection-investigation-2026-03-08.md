## Executive Summary

1. The `architect · Codex · 2026-03-08T16:04:19 · Skipped` row is not being freshly generated by the currently running app. The audit UI is reading the persisted record from `~/.claude/teams/taurhaus-team/state/compaction/architect.json`.
2. The audit IPC currently returns the last persisted record per member with no freshness or current-session filter. That is why the same old row reappears after app restart / reinstall.
3. The missing Claude reinjection is explained directly by missing hook installation in the live Claude config:
   - `~/.claude/settings.json` has no Taurhaus `SessionStart` hook entry
   - `~/.claude/hooks/` does not exist
   - the hook bridge code exists and CLI mode is registered, but installation only runs on initialize/add-agent/resume flows, not on app startup for already-existing teams
4. The canonical operational and compaction state lives under the mesh teams directory, not under Windows `%APPDATA%/com.taurhaus.dev`.
5. Runtime `session_id` values are still `null` for all members in the live team runtime files. So the #694 behavior is not reflected in the current persisted runtime state that was investigated here.

## Root Cause: False "Skipped" Trigger

The currently visible audit row is not evidence of a fresh Codex trigger in the current app session.

Evidence:

1. The app log on Windows shows repeated `coordination_get_compaction_audit` IPC calls, but no `compaction.detected`, `compaction.skipped`, `compaction.injected`, `compaction.failed`, or `compaction.stale` events in the available current logs.
2. The current app log also shows repeated `session_scanner.scan.completed` entries with `session_count: 0`, so the currently running installed app is not observing any live CLI sessions at all.
3. The exact same `architect` audit row reappeared after reinstall with the exact same timestamp. That matches persisted-state replay, not a fresh detector firing.
4. `coordination_get_compaction_audit_impl(...)` simply loads `MemberCompactionStore::load_all(...)` and returns those rows sorted by timestamp. It does not filter by app run, live session, or freshness.

Relevant code:
- [coordination.rs](/home/mstie/projects/taurhaus/src-tauri/src/commands/coordination.rs)

Behavior:
- The audit UI is a persisted "last known compaction delivery record per member" view.
- It is not currently a "fresh events from this run only" view.

So the immediate answer to "why did the Codex compaction detector fire while Claude compacted?" is:
- there is no evidence that it fired at that moment in the current runtime
- the UI surfaced an older persisted Codex record while the user happened to be watching during a Claude compact

## What Caused The Original `architect` Skip Record

This part is narrower than the stale-audit explanation. The persisted row still came from some earlier Codex compaction bookkeeping write.

What is known:

- member: `architect`
- tool shown in UI: `codex`
- stored session id: `sess-123`
- stored result: `skipped`
- stored timestamp: `2026-03-08T16:04:19.160044813Z`

The strongest supported explanation remains the same as in #692:

- `resolve_managed_codex_session(...)` can resolve a managed member on pane match when `runtime.session_id` is missing.
- later, `deliver_pending_codex_compaction_reinjection_at(...)` calls `member_is_still_attached(...)`
- that guard requires both:
  - `runtime.pane_id == pending.pane_id`
  - `runtime.session_id == pending.session_id`
- for `architect`, `runtime.session_id` is `null`
- so delivery fails closed and records `skipped`

Relevant code:
- [compaction.rs](/home/mstie/projects/taurhaus/src-tauri/src/session_scanner/compaction.rs)

One unresolved detail:
- I could not reconstruct the exact originating Codex JSONL record for `sess-123` from the current `~/.codex/sessions` corpus.
- That means I cannot prove from surviving JSONL files whether the original enqueue came from:
  - a real earlier architect compaction event in an old resumed session file that is no longer easy to map, or
  - a previous tracker reset / re-read condition in an older build

Given the currently available evidence, the exact original enqueue source remains unproven.

So the supported conclusion is:
- the currently observed row is stale persisted state
- the original skip itself was consistent with old runtime `session_id` drift
- the investigation does not prove a fresh false trigger at the time of the Claude compact

## Claude Reinjection Failure: Exact Cause

The Claude hook bridge exists in code, but it is not installed for the live team lead.

Observed live state:

- `~/.claude/settings.json` contains hooks for:
  - `Notification`
  - `UserPromptSubmit`
  - `Stop`
- there is no `SessionStart` hook entry for Taurhaus compact reinjection
- `~/.claude/hooks/` does not exist

Relevant implementation exists:
- hook handler: [claude_hooks.rs](/home/mstie/projects/taurhaus/src-tauri/src/coordination/claude_hooks.rs)
- CLI registration: [lib.rs](/home/mstie/projects/taurhaus/src-tauri/src/lib.rs)

But installation is only invoked from lifecycle operations:
- initialize team
- add agent
- resume member
- resume team

Relevant call sites:
- [coordination.rs](/home/mstie/projects/taurhaus/src-tauri/src/commands/coordination.rs)

There is no observed startup self-heal / startup install for already-existing managed Claude teams.

Therefore the exact reason Claude reinjection did not fire is:
- the live Claude installation never received the Taurhaus `SessionStart(source=compact)` hook entry
- so Claude never invoked the Taurhaus `--claude-compact-hook` CLI path
- no `additionalContext` could be returned
