# Practical Orchestration Design: Auto-Idle + Communication Quality

Date: 2026-03-06  
Owner: architect  
Task: #372

## Scope

This design solves exactly two problems:

1. Auto-idle detection + auto-nudge for assigned work.
2. Communication quality that prevents stall/ack-loop behavior.

Everything else is out of scope.

Current status note (`2026-03-09`):
- the mesh-side `IdleMonitor` loop landed
- Taurhaus now exposes runtime recovery through header actions such as `Resume Team` and `Resume Offline (n)`
- message-quality enforcement remains partly a design direction; the operational assignment checklist is standardized, but not every free-form send path is hard-linted yet

## Ground Truth Inputs (already available)

Reliable inputs already present in code/data:

- Task ownership + status from `~/.claude/tasks/{team}/{id}.json` (`owner`, `status`), with mutation journal in `state/task_mutations.jsonl`.
- Member heartbeat/activity and explicit status in `teams/{team}/config.json` (`lastActivityAt`, `statusState`, `statusSetAt`).
- Runtime health signal in `teams/{team}/runtime/{member}.json`.
- Idle reminder anti-spam marker `teams/{team}/state/{member}.idle_reminded`.
- Taurhaus process/session activity signals (tmux/session scanner + pane command/state) in `src-tauri/src/coordination/stall_detector.rs`.
- No dependency on `orchestration_v1`. IdleMonitor uses a standalone suppression helper in `mesh/src/idle_monitor.rs`.

## Problem 1: Auto-Idle Detection + Auto-Nudge

### Design Summary

Implement a small mesh-owned `IdleMonitor` loop that runs every 30s and only evaluates members who currently own active tasks.

### Candidate Set (task-gated)

For each team member, monitor only if they own at least one task with status in:

- `pending`
- `in_progress`

If no owned active task exists, skip the member completely.

### Decision Signals

For each monitored member, build `IdleDecisionInput` in `mesh/src/idle_monitor.rs` from existing fields:

- `status_state` + `status_set_at` from `config.json`
- `heartbeat_at` from `lastActivityAt`
- `runtime_health` from `runtime/{member}.json`
- `idle_reminded_mtime` from `state/{member}.idle_reminded`
- `stall_recent_activity`, `stall_no_output`, `stall_no_active_process` from taurhaus-exported activity snapshot (see split below)

Then apply this standalone decision order (no protocol module dependency):

1. Suppress when any strong-active signal is true:
- `statusState in {working, blocked, investigating}` and `statusSetAt` is live (TTL 30m)
- `lastActivityAt` freshness <= 3m
- taurhaus activity snapshot says `stall_recent_activity=true`
2. Escalate when:
- runtime health is non-healthy for >5m, or
- taurhaus activity snapshot says `stall_no_output=true` and `stall_no_active_process=true`
3. Skip repeat nudge when `state/{member}.idle_reminded` mtime is <= 10m.
4. Otherwise send nudge and refresh idle marker.

### Nudge Message Contract (automatic)

Nudge messages are generated by mesh (not manually typed) and include:

- `ACTION REQUIRED:` prefix
- explicit task id (`#<id>`) selected from owned active tasks (`in_progress` first)
- concrete first action (`Run: mesh task get <id> ...`)
- completion signal (`Update task + send summary`)
- anti-ack ending (`No acknowledgment needed; continue execution and report result.`)

This removes voluntary formatting dependence.

### Minimal State

No new protocol store needed. Reuse:

- `state/{member}.idle_reminded` for cooldown
- optional telemetry append via existing `protocol_telemetry.jsonl`
- optional taurhaus activity snapshot files under `state/activity/`

## Problem 2: Communication Quality (Enforced, Not Voluntary)

### Design Summary

Stop relying on free-form assignment messages. Provide mesh commands that generate compliant communication automatically.

### New Enforced Command Surface

1. `mesh task assign <id> --owner <member> ...`
- Atomically updates task owner/status and sends a generated assignment message.
- Message is always `ACTION REQUIRED` and includes first step + deliverable + completion signal.

2. `mesh nudge --owner <member> --task <id> ...`
- Used by `IdleMonitor`; same generated structure every time.

3. `mesh send` remains for informational chatter, but actionable usage is linted.
- If message is actionable and missing required fields, fail in enforce mode.
- `INFO ONLY` messages are auto-marked with `no_response_needed=true` semantics.

### Message Rules (hard)

Generated assignment/nudge messages must always include:

- Prefix: `ACTION REQUIRED:` or `INFO ONLY:`
- Exactly one concrete first step
- Deliverable path/output
- Completion signal
- Explicit “no acknowledgment” behavior for non-info updates

These rules directly address observed failure modes in `docs/ai-agent-characteristics.md`.

## Mesh vs Taurhaus Responsibility Split

### Mesh owns

- Task-gated idle monitor loop.
- Final nudge/escalation decision and message delivery.
- Enforced assignment/nudge message generation.
- Lint enforcement for actionable message quality.

### Taurhaus owns

- Collecting process/session activity signals (pane state, command, activity confidence).
- Persisting a tiny per-member activity snapshot that mesh reads from disk.
- UI controls/visibility for stall configuration and detector health.

### Concrete Phase C Handoff Contract

Taurhaus writes one JSON file per member at:

- `~/.claude/teams/{team}/state/activity/{member}.json`

Schema (v1):

```json
{
  "version": 1,
  "observed_at": "2026-03-06T02:51:00Z",
  "stall_recent_activity": true,
  "stall_no_output": false,
  "stall_no_active_process": false
}
```

Rules:

- Taurhaus updates every stall-detector poll (default 30s), atomic write (`.tmp` + rename).
- Mesh reads file each IdleMonitor poll.
- If missing/unparseable/stale (`observed_at` older than 120s), mesh treats snapshot as unknown and does not use it as a positive suppression signal.
- This is local filesystem only; no IPC/API dependency required.

### Why this split

- Mesh already owns tasks/messages and should own nudging behavior.
- Taurhaus already has the strongest runtime/process observability pipeline.
- This avoids duplicating process probing logic in mesh.

## Minimal Implementation Plan

### Phase A (fast path, highest impact)

1. Add `IdleMonitor` in mesh daemon loop (30s poll).
2. Gate by owned active tasks only.
3. Implement standalone suppression helper in `mesh/src/idle_monitor.rs` (no `orchestration_v1` import).
4. Auto-send Stage A nudge / Stage B escalation messages.

Expected code size: small (single service + wiring in daemon/main path).

### Phase B (communication enforcement)

1. Add `mesh task assign` + generated assignment template.
2. Add `mesh nudge` command used by monitor.
3. Add enforce-mode lint gate for actionable `mesh send`.

### Phase C (taurhaus signal handoff)

1. Export per-member activity snapshot to `~/.claude/teams/{team}/state/activity/{member}.json`.
2. Feed snapshot into mesh `IdleDecisionInput` fields.

## Acceptance Criteria

- Members with no owned active tasks are never nudged.
- Owned-task idle members are nudged automatically without team-lead manual checks.
- Repeat nudge spam is suppressed by cooldown marker.
- Unhealthy/unresponsive cases escalate to lead automatically.
- Assignment/nudge messages are generated in enforced format (no free-form dependency).
- `stall_on_ack_count` trends to zero after rollout window.
