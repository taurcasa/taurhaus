**Mesh messaging overhaul — commissioned Astra architecture study**

2026-09-07. Research only; prepared for orchestrator review under the [commissioning brief](mesh-messaging-overhaul-brief.md). No implementation or commit. The live nine-seat wave, team directories, daemon, and tmux server were neither inspected nor probed. This study reads repository source, prior research, public vendor documentation, and the installed Grok documentation only. No harness was launched, no credentials were read, and the wave-1 census was not repeated.

**Recommendation: retain messages independently of delivery, and consolidate delivery ownership before replacing transports.** Adopt one segmented, append-only **message journal per team incarnation**, with conversation IDs and explicit recipients; derive task, DM, group, and member views from it. Keep the existing task/workflow authorities. Turn inbox arrays into compatibility delivery projections only after every relevant writer is accounted for. Evolve the existing Mesh team daemon into the single delivery scheduler, with per-member queues and harness-specific adapters. Retain tmux as a bounded fallback for sessions lacking a verified native wake channel.

This preserves the strongest parts of the operator's sketch: immutable bodies, conversation identity, directed delivery, and one owner of messaging-related terminal writes. It changes two things. A task conversation need not be a physical file, particularly when one post links multiple tasks or has restricted review visibility. And a model cannot monitor arbitrary service stdout: the harness must explicitly admit that output as model input. Native channels exist, but their event boundaries, launch requirements, and acknowledgment semantics differ materially.

The first shippable stage is an **offline, pure reader and conformance packet**, disabled in normal operation, with synthetic fixtures and adapters for the locked format. It changes no live producer, consumer, hook, binary pin, or daemon. A storage migration during this wave is not warranted.

For all four harnesses, an ordinary MCP **tool result** can carry messages when the model calls a bounded read or wait tool. That is cooperative pull, possibly a long poll during an active tool call, not a universal idle push contract. MCP [resource subscriptions](https://modelcontextprotocol.io/specification/2025-06-18/server/resources) notify a host of changes; the host controls context inclusion. MCP [sampling](https://modelcontextprotocol.io/specification/2025-06-18/client/sampling) requests a model generation under client control and does not establish injection into that host's ongoing conversation. Claude's channel extension is evidence of the extra host behavior needed. No equivalent general MCP push contract was established for the other three in this inspection.

The practical retirement boundary is therefore precise: **keep Claude's existing native mailbox and Claude/Codex native compaction; trial boundary drains for Claude/Codex/agy/Grok on verified versions; retain an idle-wake fallback for current bridged TUIs.** Investigate Claude channels first where native mailbox compatibility is undesirable, then controlled Codex app-server and agy/Grok protocol hosting. Do not advertise complete send-keys retirement today. Launching, pane splitting, interrupt/stop, focus, runtime effort changes, and manual nudges remain separate runtime operations even if every message eventually uses a native channel.

Do not turn the existing workflow log into an omnibus body archive during a live protocol-1 wave. New enum variants, private body access, and retention policy affect its readers. Introduce a separately versioned **message authority**, replacing inbox body authority gradually, rather than a second editable task database. Existing workflow, protocol-index, task-mutation, ruling, lease, and assignment records remain their own authorities. Their IDs link into conversation views. A team-wide log here means one logical sequence with immutable segments, not a single ever-growing file.

Keep small text inline so body and audience are one durable record. Larger artifacts use immutable content-addressed references with size/hash and retention ownership; a mutable checkout path alone is not a retained body. Large content must be durably stored before its message reference commits. Never log provider credentials or include arbitrary environment/transcript dumps. Receipts and adapter diagnostics should carry identifiers and sizes, not another full copy of the message.

DM retention is a deliberate policy change if bodies outlive today's queue. New-format teams must declare bounded DM retention and audience at creation; existing DMs are not silently imported into shared task history. Task evidence can have longer task/archive retention. Restricted independent-review material stays restricted, including its summaries, reply previews, and artifact expansions. “DM” describes routing/visibility policy under a shared account; it is not a confidentiality guarantee against same-user filesystem access.

One message can link T3 and T4 and appear in both task views while being delivered once to a reviewer. A broadcast commits one body and the resolved roster snapshot, including inactive registered recipients except the sender, preserving current behavior. Per-recipient delivery IDs allow partial progress and retry without turning a five-recipient broadcast into five authored posts. A later recipient addition is an explicit routing/replay event, not mutation of the old audience.

**Concurrency, durability, and recovery.** JSONL is useful because completed records need not be rewritten; it is not automatically safe because it has newlines.

Use a shared validated writer library callable by Mesh commands and WSL-native hooks, with **one stable lock file per journal**, never renamed or unlinked during normal operation. Cooperative producers serialize validation requiring current state, sequence allocation, tail recovery, append, file sync, and commit-boundary publication under that lock. A later RPC writer can use the same contract. Do not require the delivery daemon to be running just to accept a message. This avoids replacing today's daemon-independent durable send with a daemon availability dependency.

Serialize each record to bytes before locking; append the bytes plus newline as one prepared buffer, handling short writes while the lock remains held. `O_APPEND` can help place writes at EOF but is not a promise that a logical record spanning writes, or a crash, is atomic. `PIPE_BUF` applies to pipes, not this file protocol. Do not rely on shared append semantics across Windows/UNC or an arbitrary network filesystem. Keep the writer on the team's native filesystem side, honoring the existing daemon boundary.

Durable acceptance requires message bytes synced, any new segment/directory entries synced, and an atomically replaced, synced manifest advertising only the committed boundary. This adds write overhead; a measured group-commit option may later amortize it, but must report “pending durability” until the group commits. Lockless consumers read a manifest snapshot then immutable segment prefixes no farther than its committed boundary. The service must never deliver bytes merely visible in the page cache but not yet published as committed.

Recovery under the stable lock validates the tail and continuity before allowing new writes. A final partial line is preserved in a diagnostic recovery artifact and truncated back to the last valid boundary; never append new JSON immediately after it. A complete valid unadvertised suffix from a writer that died before returning can be synced and published during recovery, with the original IDs retained. Its caller had an unknown outcome and retries with the same idempotency key. A conflicting payload under that key is rejected. Interior corruption or a missing segment fails closed for the affected coverage range; no silent malformed-row skip that permanently advances a reader past evidence. Unaffected teams can continue.

An idempotency index is rebuildable from committed records. It must not return success based on an unsynced cache, and pruning it must not permit an old retry to create a second accepted message. Either retain accepted keys/tombstones for the documented maximum retry horizon or reject keys older than that horizon as unverifiable. Recovery must reconcile the manifest with on-disk segments before allowing acknowledgments. A commit that outlives a lost response is an ordinary retry case, not proof of duplicate delivery.

Rotate by size and optionally age under the same lock: seal the previous segment, create/sync the next, publish the manifest and directory entry, then admit appends. Never truncate/replace a live segment behind a byte cursor. Archive sealed segments with checksums; retention removes them only after required delivery obligations and policy horizons are resolved. An inactive recipient cannot pin storage forever without an explicit policy: expiry emits an auditable undelivered/expired disposition and exposes the gap on return. There is no silent drop or success receipt.

Compaction means rebuilding indexes/checkpoints or policy-governed archival, not rewriting conversation history in place. If records must be repacked, create a new epoch with a sequence-to-position map and an explicit reset path. A stale cursor gets `cursor_expired` plus coverage and a bounded resynchronization response. A same-size file replacement must be detected by source/epoch identity; length-only checks are insufficient. Read cursors count bytes, not Unicode characters. Retain the final partial buffer across incremental reads and never advance through it.

Mixed retention classes in one segment need special treatment: an expired DM cannot be considered deleted merely because a task record keeps the segment alive. Policy-driven repacking must preserve retained event IDs/sequences, replace expired bodies with minimal permitted tombstones, publish a new epoch, and remove old body-bearing segments, backups, and derived caches under the same declared policy. An audit tombstone records intentional expiry without retaining the expired text. This is a cost of the single-log choice; neither a filter in Scope nor whole-segment rotation alone enforces per-message retention. A new-format team must not promise expiry guarantees before this path exists.

A task projection joins these message positions with independent workflow/protocol/mutation watermarks. Source event time, committed/arrival position, and first-observed time remain distinct, so a late old-timestamp record still appears as new evidence. Pagination advances only through returned evidence; hidden/folded bodies do not become “read.” No default subscriptions are added. A task view remains a bounded projection, exactly as the prior study recommends.

**Identity, authorization, and authority.** `author: "lead"` in a JSON object is not authentication. Today [actor_auth.rs](/home/mstie/projects/mesh/src/actor_auth.rs) validates registered/active member identity against locally issued control credentials and canonicalizes names. The inspected resolver can load credentials from the local member credential file. Owner-only file modes separate OS users, not cooperating agents running as the same user. Such an agent can bypass the CLI and alter files or obtain another local member credential. A raw shared-filesystem append API does not improve that boundary and could discard useful validation.

Retain actor validation at the sanctioned writer API; derive author and service principal there rather than trust the supplied name. Resolve aliases against the correct team incarnation/root. Preserve inactive-actor rejection for authored sends and existing lifecycle role/generation checks. Give Taurhaus operator notices the truthful `taurhaus` origin, and generated idle/deadline notices their service/source identities. Imported native records get claimed author plus unverified import provenance; never bless them as authenticated because they have a familiar field shape.

Strict anti-forgery or restricted-review confidentiality requires an actual process/filesystem boundary: broker-only writable storage, per-seat isolation or separately protected credentials, and enforced read APIs. A Unix socket's peer UID alone cannot distinguish nine seats sharing a UID. This is a separate security project, not a benefit to claim from JSONL, hashing, signatures whose keys share the same filesystem, or advisory locks. The recommended first stages preserve today's cooperative trust model and improve validation/auditability without claiming stronger isolation.

Message content is evidence, not executable control. A “GO” string does not clear `awaiting_go`; a “complete” post does not complete a task; a newer opinion does not override an acceptance ruling. Context-hook adapters must frame foreign body text as attributed message data, especially where a vendor injects hook output at developer/system priority. That framing reduces accidental authority confusion but is not an adversarial sandbox.

**Delivery-service design.** Use one Mesh-owned scheduler per team incarnation, hosted in the existing team-daemon process, with independently drained per-member work queues. The process holds a stable exclusive lifetime lock and a fencing epoch; stale PID files are diagnostic, not ownership. Harness-owned MCP/sidecar processes may still exist per session, but they are transport endpoints, not competing schedulers. Taurhaus remains responsible for runtime attachment, launch/liveness, and its daemon-owned coordination passes. The Mesh idle monitor remains the policy producer of operational nudges.

Do not steal that ownership on heartbeat age alone: a paused process may resume. Adapter handoff must establish that the previous executor and any outstanding terminal child have stopped, or that the receiving endpoint rejects the old fencing epoch. Tmux does not enforce a Mesh epoch, so fencing there requires local executor exclusion and child-lifetime control, not just a number in a receipt. Use a fixed lock order for any operation spanning task/runtime validation and message acceptance; never hold those locks across harness or terminal I/O. Revalidation immediately before delivery narrows races but cannot revoke content already accepted by a harness.

| Step | Contract |
|---|---|
| Accept | Authorized producer commits body, links, and complete directed audience. Return canonical message ID and durable acceptance separately from delivery state. |
| Schedule | Read committed journal delta, derive pending recipient obligations, and reconcile current task generation, declared waits, runtime attachment, and adapter capability. Filesystem notifications are hints; startup and periodic catch-up guarantee discovery after missed events. |
| Claim | Atomically claim a delivery attempt for exactly one adapter, session attachment generation, and fencing epoch. Hooks and push workers use the same claim contract. Do not let inbox, hook, and tmux each consume independently. |
| Present | Return a bounded attributed batch through a native hook/channel/protocol, publish a native inbox projection, or perform the guarded terminal fallback. Never run a model to summarize routine delivery state. |
| Record | Persist the strongest observed receipt stage with its evidence. Failure/unknown outcomes remain retryable according to adapter semantics, without pretending they were model reads. |
| Reconcile | Rebuild pending work from accepted targets minus receipts/supersession/expiry dispositions. Restart does not clear waits, invent activity, or repeat onboarding solely because the delivery process restarted. |

Writes continue while the scheduler is down; messages accumulate and ordinary explicit reads can still return committed data. Existing native mailbox projection can continue only through its designated owner, not an ad hoc emergency writer. Native hook readers may use the same local library to claim/record a batch even if the scheduler is unavailable, provided the current adapter mode authorizes that pull path. Otherwise they return empty promptly and leave the obligation pending. The already responsible launcher/supervisor restarts the scheduler; no new mutually restarting watchdog pair. Health exposes last heartbeat, pending age, stuck recipient, and adapter failures through existing diagnostics. A dispatcher outage is not an agent launch-health failure.

Keep delivery I/O off the idle-monitor loop: a hung hook endpoint or tmux child gets a timeout and cannot stall other recipients, lease reconciliation, or monitor decisions. Use bounded queues/backpressure, fairness across members, and bounded batches. Catch-up after restart is incremental; queue pressure must not launch more model turns merely to clear backlog. Exact limits and latency targets require an isolated workload test; nine seats alone does not justify a complex distributed broker.

The transport contract is **at least once for retryable accepted obligations**, with stable IDs and best-effort deduplication. Exactly-once acceptance can be enforced within the journal/idempotency contract. Exactly-once model exposure or execution cannot be promised across a crash between a harness accepting input and the adapter recording that acceptance. Hook stdout has an analogous gap: the bridge can record that it produced a response, but cannot atomically commit a receipt with the harness consuming it.

Use explicit states such as `accepted`, `attempt_started`, `submitted`, `native_enqueued`, `hook_response_offered`, `consumed_by_read`, `superseded`, `failed`, and `outcome_unknown`. Adapter support determines which states are observable. Task accept/start/progress/review/complete are separate lifecycle evidence, not the final states of a messaging receipt. A timeout after sending is unknown, not a definite rejection. Retry with the same ID; if the native interface lacks deduplication, the duplicate-exposure risk must be visible and bounded. Never automatically route an unknown native outcome through tmux as if nothing had been sent.

For hooks without a consumption acknowledgment, retain an offer/batch ID and suppress immediate repeat offers within the same verified context epoch; otherwise every tool boundary would repeat the batch. Expose unresolved offers to explicit read/recovery, and use bounded retry rules for a failed or interrupted hook. That suppresses loops but cannot simultaneously guarantee zero duplicates and zero missed exposure. The at-least-once delivery objective is conditional on a live, supported consumer eventually accepting a retry; it is not a guarantee for a permanently idle boundary-only adapter. The fallback/read path and an explicit unresolved-delivery signal are therefore part of the contract.

Ordering is commit sequence for messages addressed to a member, subject to explicit priority/expiry/supersession policy. There is no global simultaneity across recipients. Maintain causality for assignment→GO and correction→dependent action. Before presenting an old generated action, revalidate assignment identity and classify obsolete work as superseded; retain its historical body. Do not drop ordinary authored evidence because a task was reassigned. Low-priority/info traffic remains available without a wake; urgent routing is not authority to ignore an explicit dependency wait. A permitted new assignment/GO can notify a waiting seat, but only the lifecycle command changes the wait.

Receipts have different owners: scheduler transport receipts, harness/native observations, explicit agent read receipts, and human Scope read marks. Today's `read`/`ackedAt` compatibility fields cannot represent all four. Map only what is actually observed and preserve the original evidence label. A byte cursor for transport catch-up can pass an event after durably scheduling it; a user history cursor cannot pass unseen bodies. A resumed context gets a bounded current card and relevant outstanding deliveries, not a replay of everything previously read. Compaction does not reset logical recipient identity.

**The remaining tmux backend.** Consolidation removes competing messaging writers, not the shared terminal itself. Use one adapter-owned terminal injection path per member; remove direct cron/message injections as callers migrate. Launch/effort/interrupt operations retain their owners but share an exclusion mechanism with messaging so they cannot race a prompt submission. The scheduler should request runtime attachment facts from their authority, never rediscover a pane by display name.

Validate explicit tmux server/socket, pane ID, pane process PID and start time, attached session identity and harness before every attempt; revalidate after waiting. Inherited `$TMUX` must not choose the destination implicitly. Use argument-vector invocation, literal text, safe bounded rendering, and the harness-specific submit policy. A disappeared, foreign, ambiguous, or changed pane leaves delivery pending/quarantined; it is never permission to type into a guessed replacement. Preserve existing configured-CLI and effort-readiness checks.

These controls address pane drift and accidental server targeting, and centralization reduces collisions among automated writers. **They cannot make terminal injection atomic with a human editing the prompt or a harness taking over terminal input.** Busy/idle telemetry is not proof that the editor buffer is empty. If an adapter cannot establish a safe window, defer or surface the pending notice; do not clear the buffer or interrupt by default. The two-step text/submit operation also has a partial-success window. Record unknown outcomes and avoid blindly sending another full body.

The brief supplies this season's interleaving, pane identity, `$TMUX` inheritance, and pane-split incidents as field reports. This study did not reproduce them or assign rates. A messaging journal can prevent disappearance of accepted content and improve diagnosis, but cannot fix a failed pane split or a session that never launched. Runtime repair remains outside messaging. Native input adapters reduce that class of exposure; they do not eliminate session-identity errors or all launch machinery.

For lifecycle-generated messages, “journal plus task file” is still two writes. The first safe integration records/reconciles a deterministic notification key from an existing committed lifecycle event, for example transition ID + notification kind + recipient. It can repair a missing fan-out intent without rerunning the transition. Where the existing task-to-workflow mutation itself has an ambiguous crash window, report it rather than claim a transaction the source does not provide. A true task+notification transactional outbox would require a separately reviewed lifecycle storage change. It is not a prerequisite for improving authored-message retention.

Native Claude is the hardest writer-coverage seam. Its inbox remains a harness-controlled compatibility surface; a file watcher can import only what it observes. A managed outgoing tool/hook integration that captures message content before native consumption, or a channel-backed Mesh send/read path, is needed before claiming complete retained conversations. Switching on a team journal while Claude continues writing outside it produces **partial coverage**, which the projection must display. Never translate a native message back into its source mailbox on import: preserve origin mapping to prevent bridge loops.

The consumer change is additive, not a scanner rewrite. [The team parser](../../src-tauri/src/claude_code/teams.rs) reads roster/config identity; [activity exports](../../src-tauri/src/coordination/activity_export.rs) remain the existing daemon observation path. [Telemetry storage](../../src-tauri/src/coordination/stores/telemetry.rs) and [routing reports](../../src-tauri/src/coordination/routing_report.rs) consume observational sidecars rather than reconstructing all metrics from inbox text. Add accepted/attempt/receipt observations with canonical source IDs and deduplicate a monitor event visible in both old and new stores. Do not relabel native enqueue as read, or fill missing reviewer usage from message counts. Scope should consume the same bounded task projection with coverage/freshness fields and its own read marks; it need not read private journal bodies directly or become a messaging writer.

**Cost: principally reliability and latency, not an automatic token win.** Changing bytes on disk or moving the same body from tmux to hook stdout does not reduce the amount of text introduced into context. Native wake may lower polling/wake overhead and avoid accidental replies, but Stop continuation can also create extra turns. Retaining more formerly missing bodies may increase possible reads. Improved audit coverage is valuable independently of billing.

The threads study's TE estimator is characters/4, not tokenizer output. Its targeted task baseline is **21,131 TE**; participant deltas skipping one's own posts cost **35,438.75 TE (1.68×)**, participant full reads cost **152,224.25 TE (7.20×)**, and nine-seat full reads cost **786,255.75 TE (37.21×)**. This design keeps targeted delivery and optional bounded task reads, so none of those audience expansions is inherent. Storage dedup does not change their arithmetic.

A useful marginal accounting identity is: changed introduced payload + hook/channel headers + read/check output + extra continuation turns + recovery summaries, minus demonstrated avoided duplicate deliveries/relays. Price new input, cache writes, cache reads, and output separately by actual model/account. The prior full-wave lead totals of 5.16M output and about 1.292B cache reads do not establish removable notice spend. Its correlation discussion does not establish a causal input/output conversion coefficient. Do not turn the brief's approximately 0.95 correlation into a claimed savings multiplier.

The strongest savings hypotheses remain a versioned onboarding card, one complete assignment rendering, no repeated wake while a durable obligation is pending, and no-response handling for information-only notices. Measure these against an equally disciplined inbox baseline. The previous study's separately proposed 20% coordination-cost improvement threshold can govern any agent-consumption experiment; reliability work should instead justify itself with retention, correct routing, and honest receipts. If native delivery costs the same but removes terminal corruption, that can still be a successful result.

Stage 1 is **shadow capture**, not two independent truths. Stage 3 is **canonical commit followed by retryable projections**, not uncoordinated parallel writes that both claim success. A journal-first canonical send may truthfully report durable acceptance with projection pending. A legacy-first shadow send must distinguish legacy acceptance from archive coverage. Neither can be called atomic across files.

In the shadow stage, a pre-send retained intent can preserve the body before the legacy write, followed by an observed legacy outcome. An intent alone is never rendered as a successful send; a crash between those operations leaves acceptance unknown until reconciliation. Capturing only after the legacy write retains a crash gap and must say so. Cross-team relay likewise remains two independent team commits: preserve origin team/message and relay-hop IDs, apply existing destination policy, and idempotently accept the target copy. There is no global conversation transaction, no automatic cross-team audience expansion, and no forwarding an imported copy back to its origin.

Keep Mesh 0.2.29 / protocol 1 / schema 1 and Taurhaus protocol 24 fixed for the active wave. New optional read fields can follow the repository's additive/defaulted rules, but changed command response meanings, runtime delivery ownership, or incompatible persistent vocabulary require an explicit paired contract review. Do not assign a future protocol number from this memo. New on-disk messaging format needs its own version, minimum supported writer, and fail-closed writer negotiation; the old binary will not understand a new marker automatically, so operational exclusion and a compatible guard release must precede any old-team upgrade. Update the bundled Mesh pin only through the ordinary release process after integration review. Scope's read schema can evolve separately without granting the Windows app write authority.

Unit/fault tests establish software contracts, not vendor input consumption. A future permitted, isolated harness trial must prove uptake using a distinctive benign payload and the correct session's output. Do not copy credentials into fixtures or treat an old report's authenticated probe method as current authorization. The document-only study runs no build gate: `just check-quick` would format/compile unrelated implementation and adds no evidence for this memo. Review consists of source tracing, claim labeling, coverage checking, and verifying the deliverable remains untracked.

**Risks, deliberate non-changes, and open questions.** The design trades array rewrite pressure and fragile retention for a journal commit/recovery contract plus compatibility adapters. That is worthwhile only if the adapters have one owner and new complexity is validated. Main risks are incomplete capture of native Claude writes, unsupported/new harness features, duplicate exposure at crash boundaries, private evidence leaking through derived views, and a team-wide scheduler failure delaying all recipients. Bounded queues and restartability reduce that blast radius; they do not eliminate it.

The design deliberately does not replace task lifecycle, introduce automatic subscriptions, add a permanent summarizer agent, infer a ruling from conversation chronology, strengthen same-user isolation by assertion, rewrite harness transcripts, turn notices into permission approvals, or replace the launch/effort/focus subsystem. It does not promise lower token spend, stronger power-loss guarantees than implemented, or complete legacy history.

The following remain open and should gate only their dependent stages:

1. What caused the March JSONL conversion to be reverted? Review the original operator/reviewer rationale before reusing any of that code. The available commit messages do not answer it.
2. Which exact harness builds and configuration/trust modes will the next test team pin? Codex's compaction minimum is not a minimum for every hook; Grok's installed guide may be newer than the prior runtime report; public Claude team semantics have evolved.
3. Can `agentapi send-message` address a standalone agy TUI with stable busy/idle and receipt behavior? If not, retain its boundary hook plus tmux fallback, or separately evaluate stream hosting.
4. Can managed Codex app-server / Grok ACP host the existing interactive workflow with one controller, correct subscriptions/accounts, and reliable resume? A documented protocol is not proof that an arbitrary running TUI exposes an attachable control endpoint.
5. Can all native Claude authored messages be captured before consumption, or should complete retention require Mesh-owned send tools/channels? Watcher-only capture must stay labeled partial.
6. What retention policy applies to DMs, unreleased review bodies, inactive recipients, and team closure? Choose bounded policy before enabling capture, including explicit expiry behavior and archive access.
7. What actual append rate, record size, history length, and fsync latency justify a team journal over compatible retained-body records, or SQLite over JSONL? No benchmark in the prior study settles this.
8. What native receipt evidence is available without expensive transcript scanning? Until verified, offered/submitted/consumed/acted remain separate and “read” is not model comprehension.

**Confidence and final recommendation.** Confidence is **high** in the need for independent retention, explicit task/assignment links, a stable logical post identity, selective readership, and preserving lifecycle/writer authority. Confidence is **high** that service stdout alone and ordinary MCP resource notifications are not universal inbound delivery. Confidence is **moderate** in one team journal and one scheduler as the best eventual topology at this scale; that is a design judgment without load measurements. Confidence is **moderate** in documented native boundary paths and **low** in untested hot attachment/idle-wake interoperability for the existing agy/Codex/Grok TUIs.

Adopt the operator's separation of storage and delivery, improve it with a team acceptance journal and explicit receipt/authority semantics, and stage transport replacement per harness. Start with the offline reader/conformance packet, then retention/linking and delivery ownership. Advance to canonical storage and native push only when compatibility and isolated uptake tests establish the relevant contract. The immediate win is recoverable, attributable communication; token savings must still earn their own evidence.
