# Dynamic Workflows and Multi-Model Orchestration

> Exploration doc, not a commitment plan. Records what was verified about Claude Code 2.1.237/2.1.238 dynamic workflows and Codex CLI 0.147/0.149 transports, and how they relate to taurhaus's team runtime. Live behavior is the source of truth; every claim below cites a file, command, or probe log, and anything that rests on docs, binary strings, or inference (not a live run) is marked **unverified**.

## Question

1. How could Claude Code dynamic workflows (`Workflow` tool, `.claude/workflows/*.js`) be integrated into taurhaus?
2. Or is the overlap with taurhaus's own orchestration too big, and the real question is how to run non-Claude models *inside* dynamic workflows without losing communication mid-task (`codex exec` works but is deaf while it runs)? How much does mid-task communication actually matter?

## Direct answers

1. **Integrate them as the versioned *procedure* a member runs, not as a competing runtime.** Taurhaus already holds everything a workflow lacks — persistent identities, role lanes, an inbox/task bus, a canvas — and Claude Code already writes a machine-readable run tree that taurhaus can read from the member's session dir it already knows. Concretely: a `workflows/` dir in the template store, a "run workflow X" trigger over the existing operator-notice delivery, a `workflows:` role default with per-task override, and a run scanner (Design A). The two things that must happen regardless are the idle-detection recursion fix and reading the run tree. One precondition is still **unverified**: that a team member launched by taurhaus can invoke `Workflow` when told to (Experiment 1).
2. **The overlap is small, and the reframing is right but needs a correction.** Who/how split: taurhaus orchestrates *who* over days, a workflow orchestrates *how* over minutes. Non-Claude models can run inside a workflow today because workflow subagents have Bash (Design B, ladder of four transports). Mid-task communication is bought per stage, not per architecture: every transport we can drive from code is turn-granular except Codex App Server `turn/steer` (verified live), and even steer lands at the next model-request boundary. It matters in two narrow cases — long unattended turns with a watcher that has something new to say, and a worker that needs to *ask* something mid-turn (which `codex exec` cannot do at all) — and for everything else the turn boundary *is* the communication point. Details with examples under "Where mid-task communication actually matters".

## TL;DR

The overlap is smaller than it looks. Taurhaus orchestrates **who** (persistent members in tmux panes, versioned role lanes, inbox/task bus, canvas) over hours and days; a workflow orchestrates **how** (a bounded, scripted fan-out of subagents that returns one result) over minutes. They answer different questions and compose cleanly: roles = who, workflows = how, transports = comms.

The sharper reframing is the second one, with a correction: mid-task communication is a property bought **per stage**, not per architecture. Every transport we can drive from code today is turn-granular — Claude teammate inbox, `codex queue` (docs/PRs), Claude channels (docs: "delivered together on the next turn" when busy), Claude peer-session UDS (`priority:"next"`, unprobed) — except Codex App Server `turn/steer`, which was verified live; what the Codex TUI does with mesh's injected Enter mid-turn (steer vs durable queue) is **unverified**. Mid-turn input matters for long unattended implementation turns with a watcher that has something new to say, and for a worker that needs to ask back; for review/rebuttal exchanges and short stages, turn boundaries *are* the communication points. Plan for turn-granular on most stages and treat steer as an optimization for the rest — "most" is a judgment, not a measurement; Experiment 5 is the measurement.

## Facts established

**Claude Code workflows (2.1.237 parent session, 2.1.238 on PATH; 4 headless runs, 51 historical runs)**

- Script API: `agent(prompt, {label, phase, schema, model, effort, isolation:'worktree', agentType})`, `pipeline`, `parallel`, `phase`, `args`, `budget`, one-level `workflow()`. Scripts run in a vm with no fs/Node/`Date.now`; concurrency `min(16, CPUs-2)`, 1000-agent cap (tool-prompt strings in `/home/mstie/.local/share/claude/versions/2.1.238`). Consequence: the orchestration script itself cannot touch files, sockets, or other CLIs — only subagents can.
- Workflow subagents get `tools:["*"]` minus `SendUserMessage`/`Agent`/`Workflow`, so **Bash is available** (taurrivals corpus: 19,819 Bash calls across 211 subagents; also ToolSearch/WebFetch/`mcp__*` tools, so MCP reaches them). A subagent can therefore run `codex exec` or `mesh send` — plausible, but **not yet exercised from inside a workflow** (Experiment 3).
- On-disk tree per run: `<session>/workflows/scripts/<name>-<runId>.js`; `<session>/subagents/workflows/<runId>/journal.jsonl` (only `started`/`result` records, no timestamps or labels, appended live — a `result` line landed mid-run at 10:34:25); `agent-<id>.jsonl` (normal transcript with `message.usage`, model, tool calls, appended live, mtimes within seconds); `agent-<id>.meta.json` (`agentType`, `spawnDepth`); and `<session>/workflows/<runId>.json` with labels, phases, per-agent tokens/toolCalls/lastTool, status `completed|killed|failed` — **written only at completion or kill** (absent for all three in-flight runs checked; taurrivals: wf json mtime == journal final mtime).
- Parent transcript: `Workflow` tool_use, tool_result `{status:"async_launched", taskId, taskType:"local_workflow", workflowName, runId, transcriptDir, scriptPath}` at launch, and one `<task-notification>` "Dynamic workflow … completed" with the result JSON at the end. No per-agent progress lands in the parent transcript. `/workflows` (live view) is interactive-only; there is no CLI/JSON listing of runs.
- Named workflows: project `.claude/workflows/<name>.js` **verified live** (run3, `Workflow({name:'ok-args', args})`, `args` parsed from a JSON string; per-agent `agentType:'general-purpose'` recorded in meta.json). Also auto-exposed as `/name` (run4, `claude -p '/ok-args {"word":"ZED"}'`). User scope `<CLAUDE_CONFIG_DIR>/workflows/<name>.js` and plugin `workflows/` folders come from **binary strings only — unverified** (Experiment 1a). None of these dirs exist here today (`~/.claude/workflows`, `~/.claude-account2/workflows`, `taurhaus/.claude/` all absent).
- Headless works: `claude -p --model haiku --allowedTools Workflow 'use a workflow: …'` ran ($0.025, 1.4 s) — "use a workflow" in the user's words is an accepted opt-in, no ultracode needed; without `--allowedTools` the tool call is permission-denied (run1, $0.021). Probe total ≈ $0.12. Gates per binary strings (**unverified**): settings `enableWorkflows`/`disableWorkflows`/`workflowSizeGuideline`/`workflowKeywordTriggerEnabled`, session-scoped settings key `ultracode`, env `CLAUDE_CODE_DISABLE_WORKFLOWS`/`CLAUDE_CODE_WORKFLOWS`.
- Resume: `Workflow({scriptPath, resumeFromRunId})`, same-session only per the tool schema; "unchanged-prefix agents return cached journal results" is from the tool doc, **not exercised**. An "adopted"/`scriptSha256` checkpoint path (resume across session restarts) exists in strings only — **unverified**.

**Codex transports (0.147 installed, 0.149 via release notes/PRs; probes on gpt-5.4-mini, ChatGPT Pro; ~82k input tokens (~62k cached) / ~410 output total)**

- `codex exec --json --ephemeral` streams live JSONL (`thread.started{thread_id}`, `item.*` with command output and exit code, `turn.completed` with usage); 8.9 s for "reply with OK" (`scratchpad/probe-exec-oneshot.jsonl`, `probe-exec-2.jsonl`). Deaf mid-turn: no stdin/IPC into the process; must run `< /dev/null` or it blocks on "Reading additional input from stdin…". In non-interactive mode the model cannot ask a blocking question; approvals needing new input fail (subagent docs; **not live-verified**). `--ephemeral` threads cannot be resumed. `exec resume --last` reuses the thread id with prior context (5.0 s, `probe-exec-resume.jsonl`): turn-by-turn conversation with identity, not mid-turn input. Usage is reported only at turn end and cumulatively per thread.
- App Server (stdio JSON-RPC, `scratchpad/appserver-probe.py` + `.log`): `initialize → thread/start → turn/start → turn/steer{expectedTurnId}` worked on subscription auth (`planType "pro"`); steer sent at 9.15 s was acknowledged at 9.15 s, surfaced as a `userMessage` inside the same turn at 12.68 s while `sleep 5` ran (11.67–16.56 s), and changed the answer to "DONE PINEAPPLE" (turn 17.4 s). So steer is applied at the **next model-request boundary** (~3.5 s later here), not instantly. Server→client requests (`item/tool/requestUserInput` with `isBlocking`, approvals, experimental `dynamicTools` → `item/tool/call`) let Codex ask and block — **schema/docs only, not live-exercised**. `turn/interrupt`, `thread/inject_items`, `thread/resume`, multi-client subscription are in the 0.147 schema. Officially experimental; no `thread/queue/*` on 0.147 (schema grep = 0); ~9 s to first token (codex_apps MCP startup ~5 s). Only the stdio listener was probed; `--listen unix://` / `ws://` exist per `--help` but a raw-NDJSON attempt over unix left empty logs — framing **unverified**.
- `codex queue --thread` (0.149, not installed; docs/PRs only) writes to a durable SQLite queue (`thread/queue/add`); wakes idle threads, busy threads receive after the current turn completes or fails, paused after interrupt (PR #39092, #38456, #37204, #39034). Wake/next-turn, never mid-turn. Whether it reaches TUI sessions in mesh tmux panes is **unverified**.
- Mesh tmux injection (`mesh/src/daemon.rs:366-392`) does `send-keys -l` + 100 ms + Enter with no busy/idle check (`grep idle|busy|defer daemon.rs` = 0); observability is rollout mtime only (`src-tauri/src/session_scanner/idle/mod.rs:33-38`, 10 s threshold). Whether the 0.147 TUI treats that Enter mid-turn as a steer or a durable-queue submission is **unverified**.
- Reverse direction (Codex hosting Claude): only `claude -p` — verified `env -u CLAUDECODE claude -p --model haiku --output-format json "Reply with exactly: OK"` → OK, 1.4 s, claude.ai/max auth, ~25k-token fixed context per call (10 in + 2,695 cache-create + 22,307 cache-read). `claude mcp serve` exposes Claude Code's tools, not an agent (docs); Codex-as-MCP-server is deprecated per 0.149 notes (`scratchpad/codex-harness-report.md:23`). Codex native subagents can orchestrate and inherit/define `mcp_servers` (docs, **not exercised**). This is why orchestration of Claude must stay inside Claude Code.
- MCP is pull-only: a tool call happens only when a model decides to call it, so an MCP facade gives typed ergonomics but does not wake a deaf process. Mesh has zero MCP code today (`grep -rin mcp mesh/` → one doc link; no MCP crate in `Cargo.toml`).

**Taurhaus touch points**

- `RoleTemplate` has no procedure/workflow field; unknown YAML keys are tolerated (no `deny_unknown_fields`; `handoff_expectations` in `v3-developer-claude.yaml` is silently dropped), so `workflows:` can be authored today but is inert (`src-tauri/src/templates/types.rs:205-271`). Adding a field mirrors `required_artifacts` across ~14 Rust/JS sites.
- `TemplateStore` manages only `roles/`, `presets/`, `_meta/` and `.yaml` files (`storage/mod.rs:26-29, 758-772`); `.js` is neither seeded nor bundled (`tauri.conf.json:34-41`).
- Taurhaus already persists each member's `session_id`/`jsonl_path` (`stores/runtime.rs:27-42`, captured at `pipelines/initialize.rs:437-463`), so workflow run discovery is a pure derivation.
- Claude idle detection reads `subagents/` mtime non-recursively (`idle/mod.rs:187-197`, `idle/claude.rs:38-80`): a member whose main transcript is quiet during a workflow reads idle.
- No IPC sends an arbitrary message to a member; only `DeliveryRequest::operator_notice` paths exist (`commands/coordination.rs:606-628`, `pipelines/lifecycle.rs:518`, `members.rs:1160`); Claude members get an inbox-file append (`backend/claude.rs:41-56`), non-Claude go through mesh.
- User-level install precedent: `ensure_compact_hook_installed` writes `<claude-dir>/hooks/<script>` and merges `settings.json` idempotently (`claude_hooks.rs:277-299`, merge at `596-752`), called at startup and after team mutations.
- Config-dir split: Claude resolves teams/sessions/workflows under `CLAUDE_CONFIG_DIR` (here `~/.claude-account2`), mesh defaults to `$HOME/.claude` unless `--claude-dir`/`CLAUDE_DIR`/`MESH_SYSTEM_HOME_OVERRIDE` (`mesh/src/paths.rs:220-234`).
- Claude peer-session messaging is a local UDS protocol (`/run/user/1000/cc-socks/<pid>.sock`, registry `<CLAUDE_CONFIG_DIR>/sessions/<pid>.json`, 0600 token key file, NDJSON auth + `cross-session-message` frames, `priority:"next"`); `claude agents --json` lists live sessions. File modes suggest any same-user process can reach it; undocumented, `peerProtocol 1`, **not probed** (would interrupt live sessions).
- Three inbox writer disciplines already coexist (mesh per-file flock `inbox.rs:97-110`; taurhaus team `.lock` + tmp/rename `stores/inbox.rs:91-113`; taurhaus→`mesh send` `backend/bridged.rs:437-446`).

## Design A — taurhaus hosts workflows

Taurhaus keeps owning the persistent runtime; workflows become the versioned *procedure* a member runs when a task calls for it. Taurhaus adds what Claude Code lacks: distribution (a `workflows/` dir of `.js` next to roles, git-committed, installed to user scope via the hook precedent — user-scope resolution itself is **unverified**, Experiment 1a), a trigger (`coordination_run_workflow` IPC wrapping `DeliveryRequest::operator_notice` with "ACTION REQUIRED: Invoke Workflow({name,args})"), role/task binding (`workflows:` on the role as lane default, per-task override in the assignment footer `stores/operational.rs:25-36` or mesh task `metadata`), and observability (a run scanner tailing `journal.jsonl` + `agent-*.jsonl` into `LiveAgentStatus.workflow_runs`; flat list in `MeshNodeDetail` first, nested canvas nodes later — `meshLayout.js:112-132` is lead+agents only, M–L).

Precondition (**unverified**): a Claude member launched with taurhaus's `--team-name`/`--agent-name` flags must be able to invoke `Workflow` when the lead tells it to, possibly needing `--settings '{"ultracode":true}'` (helpers.rs:406-436 / models/mod.rs:233-240 is where that flag would go) or the "use a workflow" phrasing in the message. Experiment 1 settles which.

Honest limit: everything is turn-granular and fire-and-forget. The member gets one notification at the end; the lead cannot steer an in-flight workflow except by kill + resume (resume caching unexercised). Non-Claude models appear only as Bash-driven tools inside subagents. Size: M–L across ~20 files plus a private-schema scanner to maintain (journal has no labels; labels come from parsing the persisted script or the first prompt line until `wf_<id>.json` lands). Order: idle-recursion fix and `workflows/` store (S) → installer, trigger IPC, task override (S–M) → run scanner (M) → taureval fixture-repo lane with `claude -p` runner and cost columns (M; taureval has no fixture repos, no repo-state judge, no cost columns today — `spawner.ts`, `judge.ts:55-90`, `db.ts:19-45`).

## Design B — workflows host models

Run the pipeline as one `Workflow` script; each stage needing Codex is an `agent()` whose subagent shells out to `codex exec --json … < /dev/null` (one-shot) or `codex exec resume <thread_id>` (follow-up; the first turn must be **non-ephemeral**), carrying the thread id through `schema`-typed stage results and mirroring it into mesh task metadata for humans. The subagent joins mesh as `wf-<runId>` (passing `--claude-dir` consistent with the team's `CLAUDE_CONFIG_DIR`), reports via `mesh send`/`mesh task progress`, reads its own inbox between steps, and never tmux-injects (the daemon's dedup only knows its own `TmuxInjected` records, `daemon.rs:730-770`, so foreign injection double-delivers; a fourth raw inbox writer adds race surface). An MCP facade over `mesh` is optional polish, not a wake path.

Communication ladder: (1) `exec --json` one turn, deaf, cannot ask back; (2) `exec resume` turn-by-turn with context; (3) App Server `turn/start` + `turn/steer`, mid-turn, applied at the next model-request boundary — verified only over stdio inside **one long Bash call** (Bash is process-bounded; whether a subagent can keep a backgrounded app-server and talk to it over `unix://` across calls is an open question), and the only rung where Codex can *ask* (`requestUserInput`, unexercised); (4) `codex queue` wake/defer, the right upgrade for mesh's wake path, not a workflow primitive. Recommendation: rungs 1–2 by default, rung 3 behind a flag once a measured long-implementation stage shows drift cost (Experiment 5).

## How A and B compose

A and B are not alternatives. A is the **outer loop** (taurhaus: persistent identities, lanes, tasks, canvas); B is the **inner loop** (a workflow: bounded fan-out with Codex stages). The layering:

| Layer | Owns | Artifact | Granularity |
|---|---|---|---|
| Roles (who) | lane identity, context steering, defaults incl. `workflows:` | role YAML in `TemplateStore` | days |
| Workflows (how) | procedure: phases, subagents, Codex stages, budget | `.js` in `workflows/`, installed to user scope | minutes–hour |
| Transports (comms) | delivery + wake + observe | inbox/tasks (turn), `codex exec`/`resume` (turn), App Server steer (mid-turn), run journal (observe) | per stage |

### Where mid-task communication actually matters

Honest answer: less than it feels, and it has two directions that the question conflates — *telling* a running worker something new (inbound steer) and the worker *asking* something and waiting (outbound question). Examples:

- **Adversarial review** (Claude reviews, Codex rebuts/revises): the exchange *is* the turn boundary. `exec resume` is exactly right; steer would blur authorship. Turn-granular suffices.
- **Long implementation** (30–60 min Codex turn in a worktree): cost is drift — a wrong assumption at minute 3 burns 40 minutes. Steer pays only if a watcher (a subagent tailing `--json` `command_execution` items — itself a paid agent loop, since the workflow script cannot watch anything) has something new to say. The cheaper substitute is shorter turns with checkpoints (plan → implement → test as three `resume` turns) plus kill + resume on the workflow side. Scale check from the probe: the steer was acknowledged instantly but applied ~3.5 s later at the next model request, in a 17 s turn — on a turn that short it saved nothing a follow-up turn would not; on a 40-minute turn it saves ~37 minutes *only* if someone notices at minute 3.
- **Worker needs to ask** (ambiguous spec, missing credential, destructive step): `exec` cannot block on a question — it fails or guesses (docs). Only App Server `requestUserInput`/approvals can pause and wait (unexercised). This is the stronger case for rung 3, and it is per stage: stages authored with crisp inputs don't need it.
- **Human pairing**: genuinely mid-turn, but it is a TUI/taurhaus concern, not a workflow one. In a workflow the human's redirect is "kill, fix prompt, resume".

Rule of thumb: steer value ≈ turn length × probability of early drift × cost of wasted work, and it is zero without a watcher; "ask-back" value ≈ probability the stage hits an unanswerable choice × cost of a wrong guess. Both are stage properties. Note also that even the best case is boundary-granular (next model request, next tool call), so the practical difference between steer and short turns is minutes, not seconds.

Regardless of A/B emphasis, taurhaus must recurse one level in idle detection and read the run tree from the member's session dir; it must not write agent config into project dirs (mesh rule, `mesh/docs/taurhaus-integration-proposal.md:70-74`) or add a fourth inbox writer discipline.

## Open questions

- Does a running workflow survive parent exit and get "adopted" on `claude --resume`? Binary strings mention a `scriptSha256` checkpoint; untested.
- Is `wf_<id>.json` ever rewritten mid-run (cheap polling) or only at the end (tailing required)? Three in-flight runs say end-only; Experiment 2 checks.
- Can a Claude team member invoke `Workflow` at all, and with which opt-in (Experiment 1b)? Do workflow subagents inherit the parent's MCP servers and team context (TeammateMailbox)?
- When does Claude's teammate inbox deliver relative to an in-flight turn (tool boundary vs turn end)? Not verified here.
- Role-level vs task-level workflow binding: lane default with task override, or task only?
- User-scope install (`~/.claude/workflows/`) under the hook precedent vs per-project `.claude/workflows/`: does user scope resolve (Experiment 1a), how to version/sync with the git-backed store, and should mesh honor `CLAUDE_CONFIG_DIR` by default?
- Can a subagent hold an App Server across Bash calls (backgrounded process + `unix://`), or must taurhaus/mesh own the daemon and expose a CLI/MCP facade? What framing does `--listen unix://` expect?
- How does `codex exec` handle `item/tool/requestUserInput` and approvals when `approvalPolicy` is not `never` — fail, auto-resolve, or hang?
- After moving past 0.147: standardize Codex wake on `codex queue`, App Server `turn/start`, or keep tmux injection? Does `codex queue` reach TUI sessions in mesh panes? Does the TUI steer or queue on Enter mid-turn?
- Does the Claude peer UDS gate accept a message from a non-registered peer, and is it acceptable to build on a `peerProtocol 1` private channel?
- Should workflow subagents be projected into the team/inbox model at all, or only rendered read-only under the member node?
- For evals: judge on repo state vs run transcripts, and how to attribute cost across parent session (`claude -p total_cost_usd`) and subagents (`wf_<id>.json totalTokens`, whose per-agent formula was not verified)?
