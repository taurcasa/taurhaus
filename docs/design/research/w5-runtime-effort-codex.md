## Recommendation

1. **Correct the W5 capability model before implementation.** Add a runtime-effort capability separate from launch `effort_flag`, because current `CliCapabilities` only represents invocation flags (`src-tauri/src/session_scanner/cli_tool.rs:121-132`). Model at least `DirectSlash { template }`, `InteractivePicker { command }`, and `ResumeWithFlag`. Register Grok as deterministic `DirectSlash("/effort {effort}")` (`~/.grok/docs/user-guide/04-slash-commands.md:110-116`) and Codex 0.150.x as `InteractivePicker("/model")` until a parameterized or navigable automation contract is verified (installed Codex binary strings above). Keep Codex resume `-c model_reasoning_effort=...` as a guarded fallback (`cli_tool.rs:285-299`; `launch.rs:261-277`), not as the claim that Codex has no runtime control.
2. **Make `effort` and `effort_why` canonical assignment data in Mesh.** Add them at `mesh task create/assign` validation and persist them with assignment identity, because the current help has required assignment-contract fields but no effort fields (`mesh task create --help` lines 16-25; `mesh task assign --help` lines 19-30), and reassignment can legitimately choose a new effort. Project them into the generated assignee inbox message as both readable text and structured metadata, and include them in assignment/recovery/lead-board projections. This keeps non-Taurhaus Mesh assignments from bypassing W5.
3. **Do not overload Taurhaus `OperatorNotice` for task assignment.** Introduce a typed `DeliveryRequest::TaskAssignment` (or a typed adapter to native `mesh task assign`) carrying task/assignment ID, effort, and why; the current enum and bridged backend only know operator notices (`requests.rs:123-127`; `backend/bridged.rs:469-475`). Preserve the values in operational context for compaction recovery, since today's operational task/footer snapshots lack them (`requests.rs:50-106`; `stores/operational.rs:14-35`).
4. **Keep role effort and task effort distinct in UI/data.** Add assignment fields such as `activeTaskEffort` and `activeTaskEffortWhy` to the Mesh task/member projection instead of overwriting `FastAgentSnapshot.reasoning_effort`, which currently comes from roster configuration (`commands/coordination/live_status.rs:512-520`). Show a compact effort badge on the task card, the rationale in task detail, and the active task effort separately on the member node/detail (`TaskBoard.svelte:512-552`; `MeshNode.svelte:6-26`, `:113-133`).
5. **Make application auditable and fail closed.** Log task/assignment/member/tool, requested effort and rationale, selected runtime mechanism, and success/failure; refuse delivery when either contract field is absent. For Codex, do not report success merely because `/model` was typed: the command opens a picker, so Taurhaus needs a verified selection/confirmation path or must use the guarded resume fallback. (Evidence for the interactive-picker nature: installed Codex strings `Select Reasoning Level for`, `Increase reasoning effort.`, and `Decrease reasoning effort.`; W5 refusal/log requirement at `docs/design/workflows-integration-plan.md:20`.)
