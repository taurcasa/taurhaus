# Quiet information and one lead notice per source event

## Result

**[I — proposed contract, not shipped]** Accept information without creating an obligation to act, continue, acknowledge, or generate a turn. Normalize that expectation once, before choosing a delivery path. Keep the information available for the next read earned by real work. Render each logical lead notice once with its permitted source references; a workflow echo or task-metadata observation enriches that notice rather than generating another one. Assignments, actionable corrections, review requests and interventions retain their action path, subject to the unchanged legacy low-priority exception in §1. GO message generation belongs to D2’s `task go` design; stopping a runtime is outside the notice contract (D2 `T:docs/design/assignment-rendering-design.md:136`; findings `O:d4-opus-findings.md:6`, `:27`). This proposal changes neither lifecycle authority nor the five-line assignment contract. Basis: `T:docs/team-delivery-standard.md:19`, `:27`, `:31`; `T:docs/design/info-only-and-notice-dedup-brief.md:13`; source inventory below.

**[S — principal finding]** There is already a partial structured contract: INFO-prefixed sends acquire an orchestration block and workflow `kind=info`, `action_required=false`, `no_response_needed=true`. The daemon's general inbox gate instead examines assignment-message identity, `priority=low`, and empty text. It does not consult that contract. Moreover, a cron writer can append a low-priority notice and separately inject it through tmux. Merely improving role wording or setting the existing low priority is therefore insufficient across all paths. Evidence: `M:src/main.rs:562`, `:689`, `:960`; `M:src/daemon.rs:1523`, `:1654`, `:1875`, `:1898`; actual C06–C09 below.

**[I — scope and confidence]** High confidence in the source-level mismatch and M1 identity reuse; medium confidence in this bounded implementation design pending review and conformance tests. No harness wake behavior, monetary saving, M1–M3 gate, or design approval was verified in this lane. “One notice” is a projection and logical-delivery invariant, not an exactly-once model-exposure guarantee across crashes or foreign native writers. Basis: `T:docs/design/mesh-messaging-overhaul-research.md:155`, `:157`; `T:docs/operations/telemetry-contracts.md:63`.

## Recommendation

### 1. Accepted response expectation and wake policy

**[I — schema, stage 1]** Add **OPTIONAL** semantic `response_expectation: action | info`, serialized as optional `responseExpectation` in the current camelCase inbox. The prefix is the fallback authority: stage-1 explicit-info acceptance must retain an INFO prefix (render one for a flag-only request, retaining original-authoring provenance on existing observations); action flag-only input likewise gets ACTION REQUIRED. Preserve existing orchestration fields and their action-with-no-ack meaning. Record provenance (`explicit`, `prefix`, `legacy_intent`, `generated`, `legacy_default`, `legacy_low_priority`) and policy revision on existing observations. `unknown/legacy` is a normalized observation label, not a third serialized expectation enum. No new store. A stripped optional field costs telemetry provenance only for conforming stage-1 messages: prefix normalization recovers the decision. For foreign unprefixed unknown values, fall back actionable, with the explicit low-priority legacy exception below. Basis: `M:src/types.rs:12–60`; `M:src/inbox.rs:109`; C31; binding `O:d4-opus-findings.md:30`.

**[I — authoring precedence]** The expectation flag is proposed and optional (C20: unavailable today). A prefix and explicit flag may not contradict each other or structured action intent: reject at the current lint/acceptance seam before persistence, with a useful error. Authored prose GO/release/withdrawal/correction is **never classifiable as info regardless of prefix**, enforced at send by the bounded lint below. Here generated `kind` means the accepted inbox notice class, not the workflow echo’s `kind=info` projection. No `kind`-bearing **generated** notice may be classified info; generated classes are action and a downgrade attempt is rejected. This protects assignments, completion, nudges and recovery without conflating `no_response_needed` with no action. The future generated release remains D2’s `task go` body, outside this message-generation scope (`M:src/main.rs:689`; `M:src/types.rs:50–59`; `T:docs/design/assignment-rendering-design.md:136`; `O:d4-opus-findings.md:6`, `:12`).
