# taurhaus test strategy review

Independent quality architecture review — 2026-09-06.

The repository has useful tests; its main weakness is scheduling and the meaning of “green.” Promote the small tests that have caught consequential defects, retain a thin real-app gate, and stop paying for repeated setup and screenshot production as though they were independent verification. A larger suite or three consecutive passes would not have reliably prevented the watcher deadlock.

Evidence basis: read-only inspection of the requested files, test configuration, representative tests, and supporting scripts. The six recent defect accounts, the historical 44% truncation, and the three-consecutive-suite acceptance practice are **operator-provided evidence**, accepted here as facts of the review; their complete histories were not independently reconstructed. The three-run rule was not found in the inspected gate configuration. No tests or builds were run, and no CI timing history was accessed. All cost ranges below are **planning assumptions**, not measurements, unless explicitly attributed. CI jobs existing does not prove branch protection requires them; repository-host settings were not inspected.

**2. Findings, ranked by importance**

1. **A completed integration gate is more valuable than repeated partial green.** The settings-save wire failure escaped unit, integration and visual testing; SlideOver's mounted exit state escaped until real-app interaction exposed it. These justify a small mandatory real-app smoke before merge, not waiting for a milestone. Meanwhile WDIO defaults to suite bail 1 and Mocha bail enabled. The sealed manifest catches missing registration, but cannot prove that declared tests actually ran. The historical 44% truncation is an execution-accounting failure, not an argument to triple all runs. Current fail-fast exits should be treated as failures; this review does not claim WDIO currently returns success on a failed spec. Conditional skips in `regressions.js` still warrant explicit accounting, although `daemon-integration.js` now fails when an isolated worker's daemon is unavailable.

2. **The fast gate is inverted for Rust changes.** A backend task executes all 140 JSDOM files but no Rust assertions. Catalog ordering altered a launch default; `cli_renderers` caught it. Async-dispatch and writer-registration violations were caught by `module_boundary_assertions`. These are demonstrated high-yield contract checks and should run at lane completion, with affected Rust tests during edits. Keep their PR CI execution: the gap is early feedback, not absent CI. Do not delete source assertions for being “implementation coupled” when they enforce a real architectural safety rule. Do avoid approving changed goldens by rote: explicitly review default-model changes.

3. **Liveness coverage arrived after the escape and remains narrower than the failure class.** Both [filesystem watcher](../../src-tauri/src/fs/watcher.rs) and [daemon watcher](../../src-tauri/src/daemon/watch.rs) now have timeout-guarded topology-change/delivery regressions with eight-second completion bounds. Both execute through the heavy lane on every PR. Credit that repair. It does not establish whole-app progress under project add/remove, indexing, reconnect, callback floods or shutdown, nor prove all lock interleavings. Serial test scheduling does not neutralize internal production concurrency. Add deliberately coordinated contention tests and an externally bounded process exercise that verifies *continued useful work*. A ping alone can succeed while a watcher or UI path is stuck; a timeout inside the blocked executor may never fire. No dedicated sustained liveness/soak or field-progress gate was found in the inspected workflow/recipes; absence of all related assertions elsewhere is not asserted.

4. **E2E overhead and visual rigor are allocated to the wrong work.** The [headless wrapper](../../justfile) correctly uses private Xvfb, removes Wayland, and selects X11; this resolves focus stealing, not CPU/RAM/build cost. Nine boots, UI setup and blanket 3× acceptance remain. For equal-cost complete runs, removing the triple rule saves about **67% of suite execution**. Seeding eight sessions while preserving one dedicated wizard test removes eight redundant onboarding traversals; total time saved must be measured. Do not simply merge everything into one session: [WDIO's header](../../e2e/wdio.conf.js) records roughly 95 ms versus 165 ms operation latency for grouped versus one persistent session. Those are historical comments, not current measurements. Keep `maxInstances: 1` on the operator's machine until resource data supports another choice.

5. **Visual output is not automatically an appearance oracle.** The team-count pill escape proves the value of rendered review. Current visual specs capture PNGs, inspect metadata and selected DOM/geometry, sometimes compare variants within one run; no committed-image comparison matcher was found. A valid PNG can contain an invisible pill. CI screenshot generation alone will not catch that. Require explicit review of affected states, and automate narrow visibility/contrast/geometry invariants or a small stable baseline set. The universal eight categories × two reviewers × minimum-nine score is precision without demonstrated calibration; use risk-based independent review for consequential visual changes. The real-browser transition/focus issue also argues for allowing browser behavior tests where JSDOM cannot model rendering, rather than forcing every such test into a costly desktop session.

6. **There is concrete low-yield repetition, but cross-layer coverage is not inherently redundant.** `screenshots.js` and `readme-screenshots.js` occupy an entire default WDIO group; the latter saves documentation PNGs and swallows content-wait failures. A separate browser README export already exists. Move presentation-only captures out of acceptance; keep any assertions that exercise native wiring. `metrics` repeats types/lint/frontend work after normal gates. Within CI/full gates, `clippy --all-targets` followed by `cargo check --tests` largely repeats compilation analysis; retain Clippy and executable tests, benchmark removing only the redundant standalone check there. Different CI Rust cache keys and three environments add setup/compile cost, but merging jobs blindly may worsen feedback latency. A local gate followed by CI is not automatically waste: trust boundary, source revision and environment may differ.

7. **Native release and field confidence lag behind Linux coverage.** Windows is the primary release platform, while automated CI is Linux and WDIO explicitly excludes Windows. Edge fixture shots do not exercise packaged WebView2, Windows paths or WSL startup. macOS's advertised E2E recipe runs a shell smoke script, including live Claude/Codex/Grok calls, not equivalent UI coverage; its spend is outside the four-paid-WDIO-spec protection. Require a small native installed-artifact checklist before release and separate paid provider probes. Existing logs and monitors help diagnosis but do not constitute a field liveness acceptance loop. Also, current explicit Rust targets omit doctests and CI has no `--no-default-features` variant; add targeted feature checks if that configuration is supported, rather than claiming the feature-gate import test exercises both builds. Actual doctest inventory and support commitments were not established.

**3. Target when-runs-what matrix**

One completed pass is the normal acceptance bar. Evidence must identify source revision, executable hash where relevant, environment, planned/executed tests, failures, skips and elapsed/build time. Reuse it only while its inputs remain unchanged. Milestones are the pre-release breadth checkpoint below; paid experiments remain explicitly named and budgeted.

| Layer | Per edit | Per lane / task completion | Per PR | Pre-release / milestone | Post-release / field |
|---|---|---|---|---|---|
| Static + JSDOM | Affected tests/watch and relevant types | One `check-quick`-equivalent pass | Full JSDOM/types/lint once in CI | Reuse exact-revision evidence; validate production frontend build | New field regressions become focused tests |

| Paid providers / compaction | Never implicit | Named change-specific experiment only | Explicit approved budget, separate status | Only changed provider contracts or deliberately scheduled compatibility check | Named diagnosis; usage cap and wall timeout |
| Docs captures, metrics, bisectors | Capture only for documentation; bisect a failure | No blanket reruns | Publish existing timing/count evidence | Metrics reuse gate outputs; coverage only to answer a question | Track escapes, flake/skip rate and resource cost |

The critical smoke should include settings save through the **real frontend→Tauri payload**, persisted reload, SlideOver close followed by keyboard navigation, startup/project read, and daemon reconnect with subsequent useful work. Cheap payload/DOM regressions supplement these; they do not replace the boundary that actually caught the defects. Whole-suite acceptance must distinguish expected exclusions (paid lanes, explicit platform policy) from unexpected missing/skipped cases. Disable both `E2E_BAIL` and `E2E_MOCHA_BAIL` for breadth runs, while allowing local fail-fast runs to remain useful incomplete diagnostics.

**4. Top five concrete changes, ranked by expected defect-catch value and cost saved**

1. **Add a small executed Rust contract gate.** Introduce a `just` recipe selecting `cli_renderers`, `module_boundary_assertions`, and the relevant harness contracts, and make it part of code-lane completion beside affected Rust tests. Leave full Rust execution in CI. Include `lint-just-gates` in the lead gate so its integrity checks are not available only through a differently composed command. Estimated effort: **0.5–1 day**, including warm/cold timing. This promotes two independently proven defect catchers at much lower execution cost than another UI suite; account honestly for executable linking.

2. **Restructure WDIO acceptance around one smoke and one complete breadth pass.** Add mandatory small PR smoke; record machine-readable selected/executed/skipped cases and artifact identity; fail required coverage on absent prerequisites. Preserve one real wizard workflow, generate isolated post-onboarding state for other groups through supported setup paths, and retain native assertions while removing README/general capture-only work from the default behavioral suite. Stop blanket 3× acceptance; rerun only a diagnosed flaky case or deliberate race experiment. Keep headless serial execution and reuse a verified fresh build within a run. Estimated effort: **3–5 days**. This protects the settings/focus failures and stale-selector lesson while saving the largest avoidable operator cost; validate the seed path against the dedicated wizard and never bypass settings saving in the smoke.

3. **Turn watcher regressions into a bounded progress contract.** Keep both existing eight-second guards; add deterministic contention scenarios for watcher topology plus project/index/reconnect activity, then a short child-process canary with an external timeout and failure diagnostics. Assert event delivery and a real command completing after contention. Run the short pack on relevant lanes and PRs; place longer churn/soak on dedicated infrastructure before release or periodically. Estimated effort: **2–4 days** initially. This addresses the sole supplied production escape no prior layer caught; repeated happy-path suites offer less confidence per minute.

4. **Make visual review selective and accountable.** Produce only affected fixtures during normal changes, expand to the full set for global styles, attach before/after evidence with an explicit review result, and add a narrow guard for the vanished pill plus real-browser exit/focus coverage where rendering matters. Keep a stable, small baseline set only where it improves detection; do not introduce wholesale pixel churn. Reserve cross-review for new layouts/shared visual primitives instead of requiring sixteen category scores for every frontend edit. Estimated effort: **1–2 days**. This preserves the visual lane's demonstrated catch while reducing capture and review work that does not establish correctness.

5. **Require release-artifact and field evidence, with explicit costs.** Add a bounded native install/upgrade smoke checklist and attach artifact hashes plus completed suite evidence to release readiness. Separate macOS's paid CLI probes from its platform smoke and give all live experiments time/spend limits. Extend existing local structured diagnostics to detect stalled progress and preserve evidence for a reproducer; start with a controlled canary, not a new telemetry platform. Record wall time, build time, peak RSS and repeat/skip counts from existing runs before changing parallelism or consolidating CI caches/jobs. Estimated effort: **2–4 days** for the initial checklist, evidence and canary instrumentation; fully automated native UI coverage is a separate estimate. This closes the Linux-to-shipped-artifact confidence gap and makes the operator's resource constraint a measured scheduling input.
