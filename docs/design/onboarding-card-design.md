# One operative onboarding and recovery card

## Result

**[I — proposed, implementation UNVERIFIED] Adopt one deterministic, versioned `RecoveryCard`, used at initial activation and recovery boundaries.** Claim one baseline obligation per `(recipient, context)` under the existing team/runtime lock. Within that generation, deliver explicit corrections or self-sufficient assignment/state deltas; an unchanged nudge, daemon restart, or unforced reonboard returns existing status. Operator-authorized `reonboard --force` mints a new activation generation and delivers its baseline. A changed root or instruction creates a new card version and a correction in the same context, never a second baseline. Unify onboarding and compaction rendering without a new store, watcher, scheduler, summarizer, or detector. **[D]** Binding directions: `d3-opus-findings.md:5–21`; brief `docs/design/onboarding-card-brief.md:12–17,120–127`.

**[P — retained round-0 archive measurements] The opportunity is substantial but its avoidable part is not established:** the retained round-0 census reports 15 onboarding bodies / 79,700 Unicode characters / 39.812% of 200,190 retained body characters, with 53,508 same-seat surplus characters. All 15 have a journal `tmux_injected` receipt; 13 have a `message_read` join. **[U — UNVERIFIED] None can be assigned a verified context-generation transition from the inspected workflow journal.** Repeated text, successful terminal submission, and marked reading are three different observations. Evidence: the Opus reproduction report at `d3-opus-findings.md:3` and [wave-1 census](onboarding-wave1-census.json), including exact message IDs, timestamps, hashes, origins, receipt outcomes, and journal schema inventory; the original estimator and qualification are at `docs/design/mesh-task-threads-research.md:24–26,60–71`.

**[D — binding local decision] The card is optional evidence access, never required preflight.** Each directed assignment, correction, GO, and handoff must already contain what the recipient needs to take its next authorized action. Merely updating the card does not satisfy delivery. Independent-review projections exclude peer verdicts and their derivatives. Source: `docs/design/mesh-next-adjudication.md:14–19,49–56,75–80`; `docs/team-delivery-standard.md:19–31`.

### Identity and version contract

**[I] Separate the baseline obligation, stable delivery identity, and content revision.** The three-key table below fixes their roles; a content hash cannot identify a recreated team or recovered context. **[D]** Binding direction: `d3-opus-findings.md:5–6`.

```text
recipient = (team_incarnation_id, member_incarnation_id)
context   = (activation_generation, compaction_generation)
roots     = (root_authority_revision, resolved_teams_root,
             resolved_mesh_config_root, harness_account_root,
             launch_namespace, resolved_project_root)
contract  = (role_id, effective_role_revision,
             instruction_contract_revision, packet_revision)
card_key  = (card_schema, recipient, context, roots, contract)
view_key  = (card_key, assignment_token, stage_id, operative_source_revision,
             audience_policy_revision)
obligation_key = (recipient, context)
delivery_id = hash(canonical(card_key, delivery_kind))
content_revision = hash(canonical(view_key))  # receipt field, NOT delivery identity
attempt_id  = (delivery_id, attempt_number)
```

### Delivery rule and event table

**[I] “Once” means one baseline obligation per `(recipient, context)`, not exactly-once model exposure.** Atomically claim that key under the existing team/runtime lock, retaining the claimed `card_key` and `delivery_kind`. Attempt 2 after a crash first re-checks durable inbox presence by `delivery_id = hash(card_key, delivery_kind)`; if present, reconcile its receipt without appending. If absent and the transport outcome permits retry, recompose the CURRENT view under the SAME ID and record the `content_revision` actually delivered. If role/root/contract changed, use the new card key for a correction, never a second same-context baseline. Hook/terminal ambiguity remains `outcome_unknown`, with no blind second adapter. A worker repair alone creates no generation. ### Bounded corrections and supersession

**[I] A correction is an operative replacement.** Its envelope carries recipient/context, the last delivered revision as `supersedes_revision`, current card/content revisions, stable correction ID, issuing authority, scope, instruction IDs replaced, replacement values, effective condition and current source references. The single runtime last-delivered pointer supplies the predecessor; there is no replaced-range or unoffered-revision ledger. Reject stale root/recipient envelopes before submission and retain their transport disposition. A correction cannot relocate state, release GO, or authorize two roots. Sources: `docs/team-delivery-standard.md:27`; `team_roots.rs:84–91`; binding directions `d3-opus-findings.md:6,9,21`.

**[I/U — UNVERIFIED byte budgets] The baseline byte cap applies to the minimal-steering card, which drops the command catalog and full role text.** The earlier 4,096-byte proposal is not a fixed cap: every retained wave-1 card was 4,691–5,801 characters, so the cap must be set from an offline fixture over the real bundled roles BEFORE increment 1 fixes a number. Correction limits (initial candidate: 1,536 UTF-8 bytes and four changed groups) are likewise UNVERIFIED until that fixture establishes required-fact coverage. Reserve identity, operative next action/wait and correction authority before optional links; never truncate them. If a delta cannot fit, deliver one bounded current replacement view; if essential facts still cannot fit, deliver an explicit hold naming the field and owner. Sources: `d3-opus-findings.md:23`; retained census `onboarding-wave1-census.json`; `onboarding-card-brief.md:95–105`.

**[I] Latest-version-wins, with one attempt plus one automatic retry per `delivery_id`, tracked in existing delivery/receipt records.** Deliver one correction per real change; if several changes remain unoffered at delivery time, render ONE correction from the CURRENT operative card version, naming the last delivered card/correction revision as what it supersedes. Use the single runtime pointer for assigned and no-task seats, including root/role corrections. Drop correction coalescing, replaced revision ranges, offered/unoffered tracking and per-revision retry budgets. Recomposition or an identical request cannot reset the ID's attempt count. Retry only definite pre-acceptance failure, or crash reconciliation after the durable-presence check proves no append; unknown hook/terminal outcomes get no automatic cross-adapter resend.
